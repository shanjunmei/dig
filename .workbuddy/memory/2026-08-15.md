## digen context 注入限制：深度评估结论
- 该 bug 的"缺陷类别"与 context 类型无关，是作用域错误（生成器把只在内层 `func(ctx)` 声明的 `ctx` 写进了外层 provider 调用站）；但"触发面"被 context 独占，因为只有它是"运行时参数来源的值"，普通依赖都走作用域内结果变量 `dvN`。
- 用户尖锐反驳：把 `go/types` 后校验当"通用安全网"有风险——它只拦住"症状"、指向生成的 `dig_gen.go`（而非生成器源码路径），会把"生成器缺陷"这一真正该修的问题挡在感知之外，用户还会误以为是自己写错。
- 设计原则（已与用户对齐）：语义层规则（如 provider 禁声明 context 参数）是首选且具诊断性（说清 why）；`go/types` 后校验只应作"不把坏文件写进用户仓库"的最后兜底，且触发时必须显式标注为 **internal generator bug**（不是用户错误）并带上生成文件位置，绝不能伪装成"你的代码错了"。不能用后校验替代根因修复。
- 生成器 soundness 契约（用户确认、并经 loader 代码核实）：`接受的输入 ⇒ 产出 gofmt 干净且可编译的输出`。**重要修正（用户指出）**：loader 用 `packages.Load(NeedTypes, -tags=digen)` 加载用户源码（dig_gen.go 因 `//go:build !digen` 被排除），并对 `p.Errors` 检查——**用户代码任何编译错误都会在加载阶段 abort，到不了生成阶段**。因此推论收紧为**无条件**：dig_gen.go 上任何 gofmt/编译错误 = 生成器 bug，不存在"用户写错"逃生舱（照搬的用户表达式也已过类型检查）。生成器对非法输入唯一正当反应是"拒绝+诊断"。后校验触发时 100% 是内部生成器 bug，绝不可呈现成"用户代码错了"。
- 构建标签互斥原则（用户提问确认）：含 `dig.Build` 的源文件必须 `//go:build digen`，生成文件由 digen 写死 `//go:build !digen`（generator.go:31 / main.go:1629）。否则正常 `go build` 时两者都被编译、同名 `InitApp` 重声明。但**缺口**：源文件侧的 `//go:build digen` 当前只是文档约定，**代码里无任何校验/自动补**（prompts 声称"Enforced by digen"不实）。违反时 digen 生成成功、错误推迟到用户正常构建的 `redeclared` 报错——属"应在生成期拦下却推迟成用户困惑"的类问题。建议加生成期校验（缺标签即报错+Fix 提示，或自动注入）。

## 修复 visibility 误报：闭包参数/局部变量被当作未导出包级 var（2026-08-15，用户问 "var f is private 这合理？"）
- **结论**：不合理，是误报（false positive bug）。报错来自 `internal/extractor/visibility.go` 的 `checkGenerationVisibility`（行 65）。用户 `role/di.go:29` 的 `f` 是闭包参数 `dig.Invoke(func(f func() Config){ ... f() ... })` 的参数，不是包级变量。
- **根因**：`*types.Var` 既涵盖包级变量，也涵盖函数/闭包参数与局部变量。从 `checkFunctionVisibilityInClosure`（closure.go:173）路径进来时，闭包参数 `f` 解析为 `*types.Var` 且其 `Pkg()` 为定义包（如 `dig.example/role`，非 nil），于是既绕过 `pkg==nil` 守卫、又因 `isExported("f")=false` 被误判为「未导出、跨包不可用」。但闭包体本就会被内联进生成目标包，参数 `f` 根本不构成跨包引用。
- **实证**：最小 Go 程序验证 `types.Var.Parent()` 区分——包级 var 的 `Parent()==Pkg().Scope()`，参数/局部 var 的 `Parent()` 是嵌套作用域。并在隔离副本（`/tmp/example_repro`，`replace github.com/shanjunmei/dig => C:/Users/shanj/lab/dig`）跑真实 `digen . ./app`：无修复 → `var "f" is private ...`，2 failed（与用户报错吻合）；有修复 → `generated 2/2 (0 failed)`。
- **修复**：`visibility.go` 的 `*types.Var` case 加 `if !isPackageLevelVar(o) { return nil }`，新增 `isPackageLevelVar(v)`（判断 `v.Parent()==v.Pkg().Scope()`，nil Pkg 也判为非包级）。保留对「包级未导出 var」的校验；`*types.Func` 类（private_visibility/closure_private_fn）不受影响。
- **附带修复（独立预存 flaky）**：`UsedPkgs` 的 `map[string]bool→[]string` 转换不确定（closure.go:846 `functional.Keys`、types.go `populateUsedPkgs` 的 map-range），导致 `TestProcessorCacheHitProducesIdenticalIR` 偶发失败；两处在落盘前 `sort.Strings`。
